Project Overview:
    This project is a LibGDX game. It's a conceptually simple 4X strategy game for 3 players.

Game Overview:
    Victory: The organism game is a real time strategy game for three players. The board is a hexagonal grid and players spend energy to claim vertices with the organism they control. When no more moves can be made, the winner is the player with the most vertices captured.

    Energy: Players get a steady income of energy depending on the resources they control. Claiming a vertex has a fixed cost.

    Resources: There are three resource types arranged around the board with radial symmetry. Resources are associated with hexagons. Claiming all the vertexes of a hexagon claims that hex and all resources inside. The total number of resources owned has no direct effect. Being the leader in any one resource gives an energy bonus. If another player overtakes the leader, the bonus transfers to the new leader.

    For example. Let's say the resources look like this:

    player  resource 0  resource 1  resource 2
    0       5           2           1
    1       0           5           3
    2       1           1           1

    Player 0 leads in resource 0 and gets one bonus. Player 1 leads in resource 1 and 2, and gets 2 bonuses. Player 3 leads in nothing and gets base energy income.

    Tournament: The main game mode is a constant semi-random tournament. There is pool of participants greater than 3, let's say 20. 3 players are randomly selected to compete. They get a number of points at the end equivalent to the number of vertexes they captured.

    The overall tournament ranking is based on the sum of all vertexes captured.

    After some number of rounds, the bottom players are eliminated and new players are introduced.

    The main gameplay loop is open and dynamic from the player's perspective: the tournament is always going with AI players competing. A human player can press a button to make controls appear and jump into the next game. Maybe this would hijack a current AI player or maybe just cancel the game in progress.

    The human player will be in the game until they lose, at which point they can just re-enter the tournament with a fresh record.

    Control Interface: The control interface introduces a little bit of delay and momentum. At any given time a player's organism is considering which vertexes to claim next. The selection is biased by the position of a circular planchette in a circular area.

    if the planchette is centered in the circle, growth with be unbiased in all directions. The player, human or AI, can move a cursor around the circular field. The planchette follows the cursor at a slight delay.

    AI: The AI idea is where this project is really interesting. It starts with the biological observation that vision is tightly coupled to cognition. The AI follows this loop:

    - select a hexagon on the map
    - the map is roughly circular, so the hex has a corresponding position in the control circle. move the cursor to that position
    - extract local information about the hexagon: position, resources, vertex ownership
    - use that info to select the next hex and repeat

    I want to implement some simple learning as well as an evolutionary component. The individual organisms should learn. When it's time to create new organisms, use values from the winners.

What's working:

    A lot of things are working piecemeal, or a working but I need to rearrange code to work on them. Running the game in its current state, you get one AI player navigating more or less randomly around the control space. There's a bunch of code for the training but a lot of it is unwired:

    player controls - keyboard controls are working for player 1 and player 2. It's currently unwired, but it's possible to move the cursor, which moves the planchette, which influences the organism

    organism behavior - the organism basically works, it can

    - gain and spend energy
    - select vertexes based on the planchette position

    tournament behavior - I have the semirandom tournament basically working, although model persistence is currently unwired and needs work. Mostly it needs to be adapted to handle training/evolution. it has some other quirks that will need to be eliminated or incorporated. I am proud of the player naming/id mechanism I came up with

    map generation - currently unwired, there's a map creation screen that let's users design custom parameters for procedural maps.

    menu - menu basics are currently working but unwired.

    hud elements - the map, player energy bars, resource meters, player overview summaries

What's not working:

    the whole thing needs to be wired together and polished, but there are still some individual components that are far from done:
    - pause menu
    - human interface currently unwired, need to wire back up
    - tournament with 0, 1, or 2 players
    - persistent model pool for learning/evolution
    - learning
    - evolution

What to do next:

    - get restart new tournament working
    - get 1 human player working
    - get 2 human players working

What to do after that:
    - analyze current learning (dummy implementation)
    - does it have a bias?
